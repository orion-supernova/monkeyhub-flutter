JUNGLE
FIST

A real-time 1v1 fighting game you start from any chat. Challenge a friend, and seconds later you're trading hits at 60 fps with rollback netcode, the same tech that makes modern Street Fighter feel local over the internet. Working title; the fighters are our own monkeys, not anyone else's characters.

YES · BUILD FIRST

2D, Street Fighter-style

Side view, one plane, frame data, specials, combos. Fits Flutter's Canvas perfectly, works on every platform we ship, and can feel genuinely tight online.

STRONG OPTION

2.5D look

Same 2D rules and netcode, drawn with 3D models, lights and a cinematic camera. Modern Street Fighter is built this way. You can try it in the demo on the next slide.

NOT V1

Full 3D, Tekken-style

Sidestep around the arena, 3D models, a 3D engine inside Flutter. The demo has a playable version: the rules change less than you'd think, but the art and engine cost a lot more.

What you're seeing: in rollback mode your inputs act on the very next frame. The game guesses Bruno keeps doing what he was doing; when his real input arrives and the guess was wrong, it rewinds to that frame and replays forward, invisibly, before drawing. In delay-based mode everyone waits for the slower packet, so your own punches land late. That sluggishness is exactly what kills online fighters.

02b 2D vs 2.5D vs 3D

Three looks, one engine

The demo's three views run the same fight engine and the same rollback loop. 2D and 2.5D are only different renderers. 3D adds one rule, the sidestep, which rotates the fight axis around the arena. That's how a 3D fighter can still be a mostly 1D simulation, and why its netcode is hardly harder. The real cost of 3D is art and the engine, not the network.

RECOMMENDATION

Ship 2D, design for 2.5D

Build the core and netcode once. Launch in 2D to learn if people fight. Since the renderer is swappable, the 2.5D upgrade later is an art project, not a rewrite.

CHEAPEST "WOW"

Pre-rendered 3D sprites

3D-looking fighters, lit and shaded, running through the same 2D painter. No 3D engine in the app at all, works on web, and phones run it trivially.

KEEP THE DOOR OPEN

3D stays possible

Because sidestep is just "rotate the axis", a 3D mode could be added later without touching the netcode. Revisit when Flutter's 3D support is out of preview.

05 Controls · the make-or-break

Fighting games on glass are usually awful. Ours won't be.

Most phone players have never done a quarter-circle and never will. So the default has no motion inputs at all: direction + button, like a platform fighter. Experts get the classic scheme. Both ship, one toggle, same characters, same damage.

DEFAULT

Simple

  • Left half of the screen is a floating stick: put your thumb anywhere, drag to walk, flick up to jump, hold down to crouch. Hold away to block.
  • Three big buttons: Light, Heavy, Special. Special + a direction = the four specials.
  • Auto-combo on Light: mash it and you get a real 3-hit chain into a special. Damage is scaled down, so it's a crutch, not a cheat.
  • Generous 6-frame input buffer so taps during an animation still come out.
TOGGLE IN SETTINGS

Classic

  • Six buttons, motion inputs (↓↘→ + P) with the same buffer leniency modern games use.
  • Specials done the classic way deal 10% more, the standard reward for execution.
  • Gamepads (MFi, Xbox, PlayStation) and keyboard on macOS, Windows, Linux and web work in both schemes, remappable.
  • Haptic "tick" on every confirmed input on iOS, so you can feel your timing.

Rules that keep touch fair

The other player never knows which scheme you use, and matchmaking doesn't care. Buttons are placed from the thumb's resting point, not fixed coordinates, so big and small hands both work. Nothing important lives under the thumbs: health bars and timer are at the top, and the fighters stand in the upper two thirds of the screen.

06 Netcode

Send inputs, not positions. Rewind when wrong.

A fighting game is decided in single frames (1/60 s). Two things follow: the frames can't travel through our Convex backend, and we can't wait for the other player's input before drawing. Rollback solves the second; a direct peer link solves the first.

10,800
Convex writes a single 90-second match would cost if frames went through the server. Plus 50–150 ms added per hop. A non-starter at millions of DAU.
~15
Convex writes per match with the plan below: the match row, the handshake, the result and the replay. Same shape as a chess game.
~5 KB/s
Per player over the peer link: 60 tiny packets a second, each repeating the last 8 inputs so a lost packet costs nothing.

The numbers we'll tune to

  • 60 Hz fixed simulation, rendering at the display's rate (120 Hz ProMotion interpolates between sim frames).
  • 2 frames of input delay by default, adaptive 1–3 based on measured ping. Hides most small rollbacks entirely.
  • Rollback window: 8 frames. Beyond that the leading side briefly slows (time sync) instead of teleporting.
  • Plays great under ~120 ms round trip, fine to ~200 ms. Above that we warn before the fight, not after.

Prediction is usually right

Most frames, a player is still holding what they held a frame ago. Repeating the last input is correct the vast majority of the time, and when it's wrong the correction is a couple of frames, which hitstop and the 2-frame delay hide. The prototype's stats panel shows this live: at 100 ms, watch how few frames ever get resimulated.

07 Architecture

What we build, what we already have

Five layers. The bottom two mostly exist already in calls and chat games; the fighter adds a pure game core and a netcode session on top.

REUSE

Already in the app

  • Peer connections, ICE, per-device signaling (call_service.dart)
  • Data channel pattern (draw_channel.dart)
  • Match rows, start sheet, active games banner, push
  • Bot hub, how-to-play kit, haptics via AppBinding
NEW

Built for this

  • lib/fight/core/: sim, frame data, hitboxes
  • lib/fight/net/: rollback session + wire format
  • lib/fight/view/: renderer, HUD, controls
  • backend/convex/fights.ts: lobby, result, replay
WHY NO FLAME

No game engine dependency

The app already paints every board game with custom painters. A 2D fighter is two characters, a stage and particles: one drawRawAtlas call per frame. An engine would add weight, its own loop and its own input system, and give us nothing rollback needs.

08 Determinism

Same inputs, same fight. On every device. Always.

Rollback only works if an iPhone, a Windows PC and a browser compute the exact same frame from the same inputs. One float rounding differently and the two players silently watch different fights. So the core follows hard rules, enforced by tests.

Rules for fight_core

  • No doubles. Positions are integers in 1/100 px. Velocities, gravity, knockback: all ints.
  • No time. The core never reads a clock; the frame number is the only time.
  • No randomness except a seeded PRNG stored in the state (we already have one in backend/convex/games/rng.ts; port it).
  • No map iteration order, no async, no Flutter imports. A lint rule on the folder.
  • Web-safe ints: Dart on the web is JS numbers, so every value stays inside ±231 and we never use 64-bit bit tricks.

How we catch mistakes

  • Golden replay tests: 200 recorded fights, final state hash pinned. Runs on VM and on dart compile js in CI. Any mismatch fails the build.
  • Live checksums: players exchange a state hash every 30 frames. A mismatch is reported to MH Logs with both input logs, so we can replay the exact bug.
  • Fuzz test: random inputs for 100k frames, rollback at random points, assert the result equals a straight run.
  • Fast: one step() is microseconds, so 8-frame rewinds cost nothing and the whole test file runs in a few seconds.

Cheating comes almost free

Only inputs cross the wire, and both devices run the full fight, so nobody can claim a position or a hit that didn't happen. Each side reports the result plus the final hash to Convex; if they disagree, the match is a no-contest and logged. Rankings, if we ever add them, re-run disputed replays server-side by compiling the same Dart core to JS for a Convex action.

09 Game feel

It has to feel like a hit, not a hitbox

The bar is the same as the rest of the app: judged against the best, on a real device, in profile mode. Most of "feel" is a short list of tricks applied without exception.

Hitstop

Both fighters freeze 7–12 frames on contact, longer for heavier hits. The single biggest "oomph" in the genre. The prototype has it.

Shake & sparks

Screen shake scaled to damage, directional hit sparks, block sparks in a different color, dust on landing. All in sim state so rollback corrects them too.

Haptics

Light tap on block, sharp hit on damage, a long rumble on KO. Gamepad rumble on desktop. Reuses the existing haptics layer.

Sound

Short, punchy, pre-decoded, zero latency, mixed with ducking. A low-latency audio player, not the media one used for voice notes.

Readable motion

Every attack has a clear windup pose, so you can react. Line-glyph monkeys in the app's playful style, squash and stretch on landings.

Health that drains

The bar drops instantly, a red trail catches up after the combo ends, so you can read how much a combo did.

Comeback, not handicap

Meter builds faster when you're losing. No damage buffs: wins must feel earned.

Never dropped frames

Pre-rasterized sprite atlases, no blur effects, no layout during a fight. A dropped frame is felt in the hands immediately.

10 Cost at scale

Built for millions of fights a day

The heavy part of a fight happens between the two phones. The backend sees about as much as it does for one chess game.

Defaults: challenges only between friends or in rooms you're in, spectating limited to room members, replays visible to the room. No public matchmaking in v1, which also means no stranger-moderation problem.

P3
in progress

The cast

MOJO, TANK and NYX designed (roster lab) and being ported with every move. Then character select in the lobby and online, and controller support.

Later, and only if cheap to run

The rule for everything below: it must cost almost nothing on the server at millions of players. Fights already do (about 15 writes per match, the fight itself never touches the backend).

SUGGESTION

Replays

A replay is just the button presses, a few KB, replayed by the same engine. Cheap per fight, but storing them for every fight adds up, so: only on request (a "save replay" tap), kept on the device, shared as a small file in the chat. No server storage by default.

SUGGESTION

Spectating

Free during a call (the call already links everyone). Outside a call it would need a relay of inputs; skip it unless people ask.

WHEN NEEDED

TURN relay

For the pairs that can't connect directly (some mobile networks). Self-hosted coturn on the VPS; also fixes the same gap for calls. Inputs are tiny, so relayed fights cost little bandwidth.

SUGGESTION

Classic controls

Six buttons and motion inputs (↓↘→) for experienced players, with a small damage bonus. Engine work on the input buffer; the Simple scheme stays the default.

SUGGESTION

Rematch in one tap

Reuses the same lobby: one write. Cheap.

SUGGESTION

Per-friend record

Wins and losses against each friend, computed from finished match rows already stored. No new tables.
