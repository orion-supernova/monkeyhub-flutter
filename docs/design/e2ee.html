End-to-end encryption

The plan to make message content and media unreadable to our own server, without making the app any slower. The server keeps routing, ordering, membership and timing; it stops holding text, captions, files and media in the clear. This doc owns the E2EE design; backend costs are checked against the backend handbook budgets (R17), and client rules live in ui-architecture.

1. Today2. Goals3. Protocol 4. Architecture5. Data model6. Flows 7. Feature impact8. Push9. Media 10. Multi-device and history11. Speed12. Backend cost 13. Safety and moderation14. Phases15. Risks 16. Testing17. Open questions18. Decisions

Recommendation: MLS (RFC 9420) via OpenMLS (Rust, MIT), one MLS group per room, one leaf per device. Convex is the MLS delivery service: it already serializes writes per room, which is exactly the commit ordering MLS needs.

All crypto runs in a Rust crate behind flutter_rust_bridge, off the UI isolate, sharing the toolchain the vendored convex_flutter already uses. Plaintext is decrypted once and cached locally, so boot and scroll never touch crypto.

The order is 1:1 DMs first, then groups, then the long tail. Games, staff/system rooms and public profile data stay server-readable by design.

2. Goals and non-goals

Goals

  • The server, Cloudflare and anyone with a database dump cannot read message text, captions, files, photos, video, voice, locations, reply snippets or file names.
  • Forward secrecy and post-compromise security per room.
  • Every device is a full participant, with nothing like a "primary phone". Mac, iPhone, Android, Windows, Linux and web each hold their own keys.
  • A new device can read past history (opt-out), using a key only the user holds (§10).
  • No slower than today on any measured path, and faster where E2EE lets us ship inline thumbnails (§11).
  • Backend cost at or below today's budgets, with zero idle cost.

Non-goals (stated in the UI)

  • Metadata: who talks to whom and when, room membership, sizes and timing. The server needs them to route.
  • Games: the server validates moves and keeps hidden state. Move bubbles say so.
  • System and staff rooms: MH Logs, moderation and problem reports.
  • Public profile: name, handle and avatar. Friends-only, but server-readable.
  • Stories/moments and room names/avatars are not covered in v1 (phase 4).
  • Old plaintext history is not re-encrypted. It stays as it is, and a purge is a separate question (§17).

3. Protocol choice

Ciphersuite: MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519, which uses hardware AES on every target. Hybrid PQ (X-Wing) comes in phase 4 once OpenMLS ships it as stable; suites are per group, so a room upgrades with one commit.

Ordering is free here. MLS's hard part is a delivery service that never accepts two commits for the same epoch. A Convex mutation is a serializable transaction, so mls.commit accepts a commit only if commit.epoch == group.epoch. Exactly one writer wins, and the loser re-fetches, rebases and retries.

  • One Rust crate, mh_crypto, built for iOS, macOS, Android, Windows, Linux and wasm. It reuses the convex_flutter Rust build setup (vendored, patched; see memory: never pub-upgrade blindly).
  • The keystore is SQLite (WAL mode) holding MLS group state, the device identity key and the key-package private keys.
    • iOS/macOS: in the App Group container, so the notification extension can read it.
    • Android: app-private storage.
    • Windows: DPAPI-wrapped key.
    • Linux: the existing 0600 file approach, used for the wrapping key.
    • Web: IndexedDB, wrapped by a non-extractable WebCrypto key.
  • The Dart facade (lib/e2ee/) is the only thing ChatRepository calls: encrypt(roomId, payload), decrypt(roomId, ct), ensureGroup(roomId) and processCommits(roomId). Every call is async and never runs on the UI isolate.
  • The server never does crypto. It stores bytes, enforces epoch order and membership, and fans out. It does less work than today: no filter, no link regex, no preview building.

  • Plaintext payload (inside ct, protobuf): text, formatting, reply snippet, media {key, digest, mime, dims, duration, name, thumbhash}, location, GIF url, sticker ref, and the frankKey.

6. Flows

6.1 Device registration (once per install)

  1. DeviceIdentity.ensure() (exists) gives the deviceId. mh_crypto generates an Ed25519 identity key in the keystore.
  2. e2ee.registerDevice writes 1 deviceKeys row and inserts 100 key packages in one mutation (1 read, 101 writes, once).
  3. It piggybacks on the existing registerDevice / deviceLogin flow. Nothing is added to the boot path: it runs post-frame, like RecoveryGate.

6.2 Creating a room or starting a DM

  1. The creator claims one key package per member device (e2ee.claimKeyPackages, 1 read + 1 delete each, using the last-resort package if a device has run out).
  2. It builds the group locally and posts the commit, the GroupInfo and one welcome per device in one mutation.
  3. Recipient devices pick up welcomes on their next attach (one bounded query mlsWelcomes by_target, not a standing subscription) or when a push for that room arrives.

6.3 Send and receive

  1. Send: serialize the payload, then call mh_crypto.encrypt (µs). The messages.send mutation is unchanged apart from ct replacing content. The outbox stores the plaintext locally and encrypts at send time, so a retry after an epoch change re-encrypts instead of failing.
  2. Before encrypting: if mlsGroups.pendingRemovals is non-empty, the sender's device first commits those removals (§6.5). The server rejects a send whose epoch is behind a pending removal, so a removed member never receives a new key.
  3. Receive: messages:list delivers rows as today. For each new row: decrypt, write the plaintext into CacheStore and notify once per batch. If decrypt needs a newer epoch, fetch mlsCommits from the local epoch to the row's epoch first (one ranged read), then decrypt.

6.4 Chat list previews

listUserRooms drops the server's lastMessage text and ships the latest message's {id, ct, epoch} instead. The client decrypts each changed preview in a batch on a worker thread and caches it by message id, so an unchanged room is never decrypted twice. The cost is about 0.05 ms per preview, so 200 rooms take about 10 ms, off the UI isolate.

6.5 Membership changes

  • Add (invite accepted, join approved by a guardian, etc.): the server stays the authority on who may be in the room (roomMembers, guardian grants). The joiner's devices then enter with an external commit against the stored GroupInfo. The server accepts it only if the user is on the roster. This needs no online existing member.
  • Remove, leave, ban, session revoke: the server cannot commit (it holds no keys), so it is registered as an MLS external sender and appends a signed Remove proposal to pendingRemovals. The next device of any remaining member that sends or opens the room commits it. Until then, nobody can send to a new epoch that includes the removed member.
  • Periodic key update (PCS): a device self-updates a room only when it sends there and its leaf is more than 7 days old. Idle rooms cost nothing.

8. Push

Pushes carry ciphertext, not text. A push contains {roomId, messageId, epoch, ct} when ct is 3 KB or less (APNs caps at 4 KB; nearly every text fits). Otherwise it contains {roomId, messageId, fetch:1}, and the extension fetches the row through an authenticated HTTP endpoint that uses the existing rcptSig token pattern.

  • Single writer per state: the extension and the app share one SQLite keystore with WAL and a per-group row lock. The extension may advance epochs (process commits) but never creates commits; only the app does. The app re-reads group state on resume.
  • The server alert body becomes a localized fallback ("New message"), sent with mutable-content so the extension replaces it. Mentions keep the "mentioned you" prefix, derived from the plaintext mentions[].
  • Burst rule (alertBurst.ts) is unchanged: it is timing only. Open item: the inventory found the macOS project embedding the NSE while alertBurst.ts says the Mac has none. Resolve that before phase 1.

9. Media

  • Per-file random 256-bit key, using chunked AEAD (AES-256-GCM in 64 KB segments, each with its own nonce and index, STREAM construction). This allows progressive video playback and HTTP range requests from the existing Cloudflare/Convex URLs.
  • Encrypt while uploading (streaming, no second copy in memory). Encrypt after the existing client shrink/compress. Compressing encrypted bytes is useless, so compress first and encrypt second.
  • Integrity: the SHA-256 of the ciphertext goes inside ct and is checked before display.
  • Thumbhash inline (about 30 bytes) inside ct, plus, for images, a micro-preview of at most 2 KB. The bubble paints an exact-aspect blurred preview before the blob arrives, which is faster than today (there is no thumbnail at all now).
  • Dedup and forwarding: one blob, one key; forwarding reuses both.
  • Server-side quotas, reaper and refs are unchanged: they work on storageId and size, never on bytes.
  • Avatars: stay public (profile non-goal). Their 326 KB size is a separate fix (handbook budget: 20 KB thumbnails).

10. Multi-device and history

MLS on its own gives a new device no history. That is unacceptable for an app people use on a Mac and a phone at the same time, so:

  • The account archive key (AK) is a random 256-bit key per account. Each time a device enters an epoch, it uploads that epoch's encryption_secret wrapped under AK into epochBackups. The cost is one small write per epoch per user. Epochs change only on membership or key updates, not per message.
  • A new device gets AK in one of two ways:
    • Device link (default): the existing deviceLoginRequests approval. The approving device sends AK to the new device's identity key, sealed with HPKE.
    • Recovery phrase: AK is also stored wrapped under HKDF(phrase, "mh-archive-v1"). The phrase is about 132 bits of entropy, so no password stretching is needed. This is a different derivation from the password-reset hash, so the server's stored hash reveals nothing. A phrase rotation re-wraps AK.
  • History download: the new device downloads epochBackups, decrypts the server history it needs (lazily, per room on open), then joins the current epoch by external commit.
  • Trade-off, stated plainly: AK plus a server dump gives full history. That is the same model as WhatsApp and Matrix backups. There is a per-user setting, "Keep history on new devices", default on. Turning it off deletes that user's epochBackups.
  • Child accounts have no recovery phrase, so AK comes only through device link from an already-paired device. Guardian pairing is unchanged.

11. Speed: the rules that keep it fast

Rules

  1. Boot never decrypts. CacheStore holds decrypted plaintext, so the local-first open (2026-11-15) is unchanged.
  2. All crypto runs in Rust on worker threads. The UI isolate only awaits.
  3. Decrypt once per message id; results go to the cache. Scrolling never decrypts.
  4. Batch decrypts per delivery, with one notifyListeners per batch.
  5. Commits are fetched lazily (on open, push or epoch gap), never from a standing subscription.
  6. Key-package refill, epoch backup and self-update run post-frame and coalesced.
  7. Store ciphertext as v.bytes, never base64 (saves a third of the wire size).

13. Safety, moderation, children

  • Reports use message franking. The sender puts a random frankKey inside ct and the server stores frank = HMAC(frankKey, plaintext ‖ roomId ‖ senderId) on the row. A report sends the plaintext and frankKey, and the server recomputes and verifies. Staff therefore get authentic evidence only for what a participant chose to report. collectEvidence context messages are franked the same way, and media evidence is the reporter uploading the decrypted file.
  • Children: the filter moves to the receiver. The word list ships in the app. A child's own device masks or blocks incoming text and its outgoing text before encrypting. The receiver-side check is the guarantee, because a modified sender cannot bypass it. Policy toggles (mediaEnabled, location and so on) are metadata checks and stay server-side (guardOutgoing checks type). Filter hits on a child device can still auto-file a franked report.
  • Verification: per-contact safety numbers and a QR in the profile. A change of device keys posts a local system bubble ("Ayşe added a new device"). Key transparency is phase 4.
  • Staff and system rooms (MH Logs, moderation, problem reports) stay plaintext. The client redactor already runs before logs leave the device.
  • Export compliance: standard algorithms, so the mass-market exemption applies. Set ITSAppUsesNonExemptEncryption plus the exemption on iOS and macOS (see the memory note: a missing key silently hid a macOS build). The France declaration is needed if the app is distributed there.

15. Risks

NSE and app racing on the keystore. Two processes advance the same group. Mitigation: SQLite WAL, a per-group lock, and the extension may process commits but never author them. Verify with a stress test in phase 0.

Epoch desync / forks. Prevented by the server's epoch == check in one transaction. A device that is stuck (state lost or corrupted) self-heals by external commit, and its local mlsGroups state is rebuilt from GroupInfo.

Lost devices and lost keys. A reinstall is a new device: it joins by external commit and gets history from AK. The stale leaf is removed by the server's proposal when its session is revoked or expires.

Rust on every target. The convex_flutter build is already fragile (vendored patches, macOS Rust build). mh_crypto must live in the same workspace, with the same pins, and in CI for all six targets. Native code is uncompiled until the user builds; do not run builds from chat.

Web key durability. Cleared site data means a new device. That is acceptable with AK history; the UI says so.

Moderation reach shrinks to what participants report. That is the intended trade-off, and the filter on children's devices covers the policy goal.

Large groups and new-device bursts. A user in 500 rooms adds a device, which means 500 external commits. These are batched (25 per mutation, self-rescheduling) and the rooms show content as each one lands, most recently active first.

16. Testing and measurement

  • Rust: protocol unit tests, fuzzing of decrypt and commit parsing, and cross-target vectors (the same ct decrypts on every platform).
  • Dart: a fake Convex with multi-device scenarios. Cover:
    • the outbox across an epoch change
    • a push decrypt before the app has processed the commit
    • a removal racing a send
    • a new device restoring history
    Run only the touched files, per the test-scope rule.
  • Backend: convex-test for epoch serialization (two concurrent commits, exactly one wins), roster gating of external commits, sweeps, and reference rules.
  • Diagnostics (no content): per-device counters for decrypt failures, epoch gaps, NSE fallbacks and time to first decrypted preview, sent through the existing diagnostics path. The phase 2 gate reads them.
  • Devices: the VoIP/NSE test protocol (deploy backend, install, restart both phones, open once) applies. Render a PNG of the lock/verification UI before calling it done.

17. Open questions

History on new devices: default on via AK (recommended for Mac + phone), or Signal-style no history?
Web in phase 1: include it (wasm, weaker key storage, history via AK), or keep encrypted rooms app-only on web like secret rooms?
Reactions in phase 1: accept plaintext emoji until phase 3 (recommended, small leak), or block phase 1 on encrypted reactions?
Old plaintext history: keep it as is (recommended), or offer a per-room "remove unencrypted history from the server"?
Games: confirm that they stay server-validated and labelled "not end-to-end encrypted".

18. Decisions

  • 2026-11-15 MLS via OpenMLS over libsignal: AGPL is incompatible with a closed store app; MLS handles multi-device and groups in O(log n); Convex transactions give the linear commit order MLS needs.
  • 2026-11-15 Compression before encryption only, and only where it helps (media is already compressed; text is too small). There is no general "zip packages" layer.
  • 2026-11-15 The server never does crypto and gains no standing subscription for E2EE. Commits, welcomes and backups are all fetched lazily.
